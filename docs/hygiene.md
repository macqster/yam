# Repo Hygiene

## Baseline

- Rust code in `src/` is the active implementation tree
- `Cargo.toml`, `Cargo.lock`, `src/`, `assets/`, and `docs/` are the tracked surface
- the old reconstruction archive has been removed

## Rules

- keep changes logged in `docs/LOG.md`; when a change is user- or developer-visible enough to belong in a release summary, add a short curated entry to `CHANGELOG.md`'s `Unreleased` section too — `docs/LOG.md` stays the detailed append-only record, `CHANGELOG.md` stays the terse Keep-a-Changelog-style summary, and neither should try to be the other
- keep commits focused
- keep `AGENTS.md` procedural and pointer-heavy; it should describe how agents work in the repo, while architecture facts stay in the owning docs
- keep repo-local `skills/*/SKILL.md` files short and workflow-focused; they should trigger repeatable work modes without becoming alternate contract docs, and their names and frontmatter descriptions must pass `scripts/check-docs.sh`
- keep repo-local skill `agents/openai.yaml` files present, short, generated from the matching skill name when practical, and valid under the interface metadata checks in `scripts/check-docs.sh`
- keep build output out of version control
- do not reintroduce old runtime artifacts without a clear reason
- avoid hidden coupling between engine, render, and UI layers
- use uppercase markdown filenames only for front-door docs or similarly high-visibility entry points; prefer lower-case names for routine contracts and archive notes
- "must" means an invariant, "should" means a recommendation, and "is" means a descriptive statement
- if a concept appears in more than one active doc, one doc must be canonical and the others must link to it
- any behavior change must update the owning contract doc in the same change
- terminology is part of the contract surface; do not introduce synonyms for `world-space`, `screen-space`, `vines`, or `RenderState`
- visual hygiene matters: preserve legibility for glyphs, letters, numerals, stats, and dense simulation data; avoid decorative clutter that harms scanability
- prefer existing Rust/ratatui tools, plugins, and scripts where they keep the interface cleaner and more maintainable
- keep Rust as the runtime core unless a different tool clearly improves research, registry authoring, or offline analysis; sidecar tools are acceptable for botanical research, species data preparation, and batch inspection, but they should not replace the live simulation/render path
- Lua plugins or scripts are acceptable as a bounded extension layer for species authoring or debug/dev tooling, provided Rust remains the host, the canonical state owner, and the deterministic runtime path stays unchanged
- temp files and shared runtime artifacts used by tests or helpers should be isolated per run when practical
- boundary changes should add a negative test when practical so forbidden behavior stays explicit
- before trusting a new regression test, prove it can fail: temporarily revert the fix, confirm the test fails with the expected symptom (not an unrelated error), then restore the fix; this is cheap insurance against a test that passes for the wrong reason, not full TDD
- prefer explicit, non-wildcard match arms for core enums such as `WorldKind` (one arm per variant, or an explicit multi-variant arm, rather than a trailing `_ =>`); adding a variant then makes the compiler enumerate every call site that needs attention, which is a stronger completeness guarantee than grepping for call sites by hand
- this is a terminal application with no dev-server/browser equivalent for "run it and look at it"; verify interactive/visual changes by driving the real release binary in a detached `tmux` session (`tmux new-session -d`, `tmux send-keys` for input, `tmux capture-pane -p` to read the rendered terminal as text) and inspecting the captured output directly; treat this as a one-off manual spot-check, not a regression test, and write a real automated test if the same visual claim needs to be reasserted later — `scripts/tmux-smoke.sh KEY [KEY...]` wraps this exact recipe (boot, wait out the boot animation's Coalesce+Bar phases, send each key with a delay generous enough that state-gated key pairs like `d` then `w` don't drop the second press, capture, clean up) so it doesn't need re-deriving by hand every time
- when a working tree accumulates several logically distinct changes that should land as separate, individually-reviewable commits rather than one large diff, split by git hunk rather than by hand-editing files back and forth:
  1. `git diff -- <file> > /tmp/full.diff`, then copy the specific `@@ ... @@` hunks that belong to one concern into a separate patch file (keep the 4-line `diff --git`/`index`/`---`/`+++` header on each patch)
  2. `git apply --cached --check /tmp/concern-a.diff` to confirm it applies cleanly against the current index, then `git apply --cached /tmp/concern-a.diff` to stage just that slice
  3. before committing, verify the *staged* state actually builds and passes tests in isolation — not just the full working tree — with `git stash push --keep-index -u`, which reverts the working tree to match the index while keeping the staged slice intact; run the project's verification commands, then `git stash pop` to restore the rest
  4. repeat for the next concern (`git add <file>` now captures exactly the remaining diff between the index and the working tree, no new patch file needed, since the previous concern is already committed)
  - a match statement's hunks (e.g. one enum variant's arms across several functions) are usually contiguous and separable this way even when they share a file with an unrelated change; test-only accessor-rename hunks and new-feature hunks rarely overlap on the same lines even in the same file
  - do this only when the split is genuinely meaningful (e.g. two independent features that happen to touch the same file); don't invent artificial boundaries in an otherwise-atomic change just to have "more commits"
- use `cargo fmt --check` for docs-only or wording-only changes; run the full test suite for compositor, camera, overlay, or other shared-rendering behavior changes
- run `scripts/check.sh` for Rust hygiene; it fails if `src/core` or `src/systems` imports scene, render, UI, or terminal modules — both are held to the same upward-dependency rule, matching `docs/architecture.md`'s Forbidden Coupling list rather than only its `scene/` half — then runs format, clippy (`--all-targets --all-features`, so lints inside `#[cfg(test)]` modules are enforced too, not just the default binary target), and cargo check (the former `crate::scene::coords` isolation guard was removed on 2026-07-21 along with the now-retired `scene::coords` module it was guarding). The boundary checks use `grep`, not `rg`, on purpose: the previous `if rg …; then fail; fi` form read a missing ripgrep as "no matches" and reported success having inspected nothing, and BSD grep returns the same exit code for a missing directory as for a clean one, so each check also counts the files it scanned and refuses to pass on zero. Keep any new boundary check in that shape rather than reintroducing a bare `if <search>; then` guard
- run `scripts/verify.sh` for the full maintenance/release gate; it composes the active docs check, the Rust hygiene gate, and the full `cargo test --quiet` suite in one repo-owned command
- an opt-in `pre-push` hook that runs `scripts/verify.sh` before every push lives in `scripts/git-hooks/pre-push`; enable it safely for this clone with `bash scripts/install-hooks.sh` and verify it without changing state with `bash scripts/install-hooks.sh --check`. The installer writes only this clone's local `core.hooksPath`, refuses to overwrite a conflicting local setting, and never touches global Git configuration. Skip a single push with `git push --no-verify`; the hook is not enabled by default because it adds real wall-clock time to every push and that tradeoff should be an explicit choice, not a silent default
- `.github/workflows/verify.yml` runs the same `scripts/verify.sh` gate in CI on every push and pull request targeting `main`; unlike the opt-in local hook above, this one is always on and is enforced by branch protection on `main` (required status check, no force pushes, no branch deletion) rather than being a per-clone choice
- that same workflow also runs `cargo audit` (via `taiki-e/install-action`) against `Cargo.lock` for known RUSTSEC vulnerabilities; run it locally too after touching dependencies (`cargo install cargo-audit --locked` once, then `cargo audit`) rather than waiting for CI, and prefer trimming a crate's default features (as done for `image`, which only needs its `gif` feature here) over accepting a vulnerable transitive dependency that a narrower feature set would drop entirely
- active markdown docs should stay clean under the repo-configured `cSpell` dictionary and `markdownlint` rule set (the rules, applied by the `markdownlint-cli2` CLI); fix real typos and malformed markdown, but prefer adding recurring valid repo vocabulary to shared config rather than repeatedly rewriting good technical terms
- run `scripts/check-docs.sh` for docs-hygiene batches; it enforces the active root/front-door docs, `AGENTS.md`, repo-local `skills/*/SKILL.md` workflow files, required skill frontmatter and `agents/openai.yaml` interface metadata, the first-level `docs/*.md` contract surface, the `docs/chatgpt-0.4-source-pack/*.md` upload-pack surface, `TODO.md` -> `known_issues.md` issue-link consistency, the canonical `Cargo.toml` -> `README.md` current-release version match, and README local-asset path validity directly, and it also runs repo-configured `cspell` / `markdownlint-cli2` checks when those CLIs are available in the local environment
- a local hook is only a verification convenience: it does not establish machine-exclusive GitHub merge authority. Device-origin work remains on its review branch until an approved `mbp` or `imac` host independently reassesses the candidate and records the disposition; CI is the source backstop
- `markdownlint-cli2` and `cspell` are npm packages, not part of `Brewfile`; install them once per machine so `scripts/check-docs.sh` actually runs those checks locally instead of skipping them. CI uses the plain `npm install -g markdownlint-cli2 cspell` (see `.github/workflows/verify.yml`), which needs a writable global prefix. Where `npm config get prefix` returns a root-owned path such as `/usr` — the case on the current Arch workstation — install into the user prefix instead of reaching for `sudo`:

```bash
npm install -g --prefix ~/.local markdownlint-cli2 cspell
```

- that form is preferred over `npm config set prefix ~/.local` because it needs no write to `~/.npmrc` and leaves global npm behavior unchanged for everything else; `~/.local/bin` is already on `PATH` here, so both CLIs are picked up by `command -v` with no further wiring. The trade-off is that it is per-invocation: a later `npm install -g` without `--prefix` will still try the root-owned path and fail
- linter versions are unpinned in both CI and local installs, so the two can drift; if a docs batch passes locally and fails the same check in CI, compare `markdownlint-cli2 --version` / `cspell --version` against the CI log before hunting for a content difference
- a skipped linter must never read as a pass: when either CLI is missing, `scripts/check-docs.sh` prints an explicit `SKIPPED` summary naming which linters did not run and states that markdown and spelling were not checked, instead of the old unqualified "All docs checks passed". Set `YAM_DOCS_STRICT=1` to turn a missing linter into a hard failure; CI sets it in `.github/workflows/verify.yml` so a broken install step cannot let the pipeline report success while linting nothing
- only `markdownlint-cli2` is invoked, not the older `markdownlint` CLI. The two ship in different npm packages (`markdownlint-cli2` vs `markdownlint-cli`). The `markdownlint` invocation did run historically — `markdownlint-cli` was installed on the previous workstation on 2026-05-19 through the tracked dotfiles/Homebrew path — but it went dead when CI arrived installing only `markdownlint-cli2` and when the current workstation never got either. Both CLIs read the same `.markdownlint.jsonc` and apply the same rule set, so keeping both would only lint every file twice
- `npx --yes markdownlint-cli2 …` / `npx --yes cspell …` work without a global install and are a reasonable way to spot-check docs on a machine you do not want to configure; the scripts deliberately do not fall back to `npx` themselves, because a local gate should not make silent network calls or stall on a cold npm cache
- findings produced without a working Rust toolchain (no `cargo`, blocked network to crates.io/rustup, etc.) must be labeled as inferred/unverified in the doc that records them, not stated as settled fact; text-based inspection of `Cargo.lock` or source files is a reasonable fallback when no toolchain is available, but it has produced concretely wrong conclusions before (a duplicated-dependency-graph claim and a stale test count both turned out inaccurate once checked with real `cargo`) and should not carry the same confidence as a toolchain-verified finding
- dated readiness snapshots (`docs/audit.md`'s `Last reviewed`, `docs/greenhouse-roadmap.md`'s `Last checked`, and similar) should state which specific claims were re-verified in the current pass versus carried forward from a prior pass, rather than bumping the whole date stamp after only checking part of the snapshot; a partial re-check that silently reads as a full one is worse than an explicit partial note
- opt-in diagnostics logs should stay local-only and out of the repo; the current path is the user state dir (`$XDG_STATE_HOME/yam/diagnostics.ndjson` or `~/.local/state/yam/diagnostics.ndjson`) behind `YAM_DIAGNOSTICS=1`
- when diagnostics are enabled, prefer the installed `yam-diagnostics` helper for quick local inspection instead of ad hoc repo scripts; keep the format simple enough that raw NDJSON stays readable too
- prefer repo-level spell/lint configuration for recurring terminology; use file-local `cspell:ignore` comments only for narrow local exceptions that would add noise to the shared dictionary
- avoid link-like bracket labels such as `[fix]` or `[12:34]` in docs unless they are real markdown links or task checkboxes; use code-style labels like ``fix`` or ``12:34`` for lightweight tags and timestamps
- front-door and active contract docs should prefer broadly readable English, while archive/history docs may keep source-accurate jargon, tool names, and quoted vocabulary as long as the shared spell/lint config recognizes them
- front-door docs must not reference local preview/media assets unless those files are committed at the referenced paths
- soft feature freeze: prefer polish and stability work only; avoid new features unless they fix a correctness bug, a regression, or a contract violation
- pre-new-feature gate: before starting any new feature, verify the modal/UI state is clean, camera behavior is explicit, hero rendering is stable, docs/logs match the current contract, and the relevant regression tests still pass
- prefer explicit error handling at real boundaries (parsing external input, I/O, network) over `.unwrap()`/`.expect()`/`panic!()`; inside `core`/`systems`, an unwrap on a value whose absence would mean an already-broken invariant (not a reachable runtime condition) is acceptable, but write the invariant in a comment or the type itself so a reviewer can tell "can't happen" from "didn't handle it" — this repo has twice found real panics from that exact gap (`GreenhouseState::active_room()`, `systems::fields::update_fields()`) where an invariant was enforced only at construction while the backing field stayed public and mutable
- `#[allow(dead_code)]` is expected on forward-built API surface (accessors for a variant or family that exists but has no caller yet, matching this repo's own pattern of building the full shape before every call site lands) — but periodically grep for it (`grep -rn "allow(dead_code)" src/`) and re-check each one against current call sites; an allow that was honest when written can quietly become a way to hide a genuinely orphaned method, and the compiler's own dead-code lint can't warn you once it's suppressed
